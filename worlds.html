Worlds and Multi-world

A world is one running copy of the game: a map, a set of players walking it, and a set of rules the world owns. Greenhaven can run many worlds on one database, and every world shares the accounts and characters that live there.

What one world is

  • A world id. A short name that ties a running process to the data it owns. Two worlds with the same id would fight for the same rows, so an operator picks one id per world and never reuses it.
  • A map. A JSON file the world loads on boot: tiles, height, spawn, respawn, characters, resource nodes, signs, chests, campfires. A world does not paint its map at runtime - it ships one.
  • Its own players. A wanderer can stand in exactly one world at a time. The player table a world holds is the players currently walking on it.
  • Its own nodes. When a rock depletes on world A, the depleted state is world A's - a copy of that rock on world B stays full.

What all worlds share

The database is one shared store with a world id on the rows that differ per world. Characters, accounts, guilds, friends, and the admin flag are shared. Every character row carries the id of the world it is currently on, and one world at a time can hold the lock on a character's save.

The lock and the autosave

  • current_world. The world a character is walking now, or the empty string when they are logged out.
  • locked_by_world. Which world holds the write lock right now. A world that finds its own id in that column knows it can save; a world that finds somebody else's id knows to stand down.
  • save_version. A monotonically increasing integer. Every save bumps it; a save that arrives with the wrong version is refused rather than stomping a newer row. This is optimistic locking - the world that wrote last wins, and any other world sees the mismatch and stops.
  • last_heartbeat. A timestamp written every tick, so a world that stops heartbeating is visibly stale. Another world can take over a character whose last heartbeat is far enough behind.

How a character moves between worlds

The picker on the menu lists every world an operator exposes. Choosing a different world from the one you are on releases the current world's lock, and the new world takes the character row by loading its last saved state. A cross-world admin action (a /give from an operator in world A to a player standing on world B) reaches world B through a notify channel world B is listening on; world B applies the gift and writes the row.

Resource nodes and world state

A depleted tree, a mine that has run out, or a fishing spot on cooldown is per world - the row keys are (world_id, map, x, y). Two worlds running the same map file do not share a node state. A world restart returns every depleted node to whatever its respawn timer said it should be, and nothing else changes.

Guilds and friends

Guild membership and friend lists ride on the shared account and character rows, so a guild is cross-world: every character on the guild roster is visible from any world, and a chat line a player sends is tagged with the guild they belong to in either. Players on different worlds do not see each other walk - that is what a world is for.

One binary, many worlds

The world server binary is the same everywhere. What makes a world a world is its id, the map it loads, and the operator's config for what other worlds it should notify. That is why an update ships once as a new build and every running world picks it up on its next restart.
