Accounts, Passwords and Sessions

Creating an account takes a username and a password. Logging in takes the same two, plus a session token that lets the client come back without retyping. This is what each of those steps does and does not store.

The account row

An account in the world's database has five fields:

  • id. A short, opaque identifier. The row's primary key.
  • username. Unique across every account on the same database. Case sensitive - "Otter" and "otter" are two different names, and the register and login cards both say so.
  • password_hash. Not the password. A hash of the password, computed with Argon2id - a slow, memory-hard key-derivation function. A stolen database hands an attacker a hash, not a password, and Argon2 makes brute-forcing that hash expensive.
  • created_at. When the row was written.
  • last_login. When the account last signed in.

Register

  1. The client sends the username and password to the world.
  2. The world checks the username is not taken and both fields are the right shape.
  3. The world hashes the password with Argon2id (a random salt per account). The plaintext is thrown away; only the hash is written.
  4. The row is saved, a session token is minted, and the client signs in on the spot.

Login

  1. The client sends the username and password.
  2. The world looks up the row, recomputes Argon2id on the submitted password against the stored hash, and compares. A match means the password was correct.
  3. On a match, the world mints a new session token and returns it. On a mismatch the world returns "wrong username or password" - never which one, so a probe cannot enumerate accounts.

The session token

A session token is a long random string the world hands the client after a successful register or login. It is not the password. The client sends it on every subsequent join instead of the password, and the world matches it against the row that issued it. This means:

  • The password crosses the wire once, on the first login, over TLS.
  • Every later join sends a token, not a password, so a stolen session cannot be traced back to a password.
  • A token can be revoked (logout, ban, admin action) without touching the password. The user does not have to pick a new one.
  • The Resume session path skips login entirely: send a still-valid token, get back into the world.

"Remember me", honestly

The login card has a Remember me checkbox. It remembers the username on this device so you do not have to type it again. It never stores the password - you still have to type it once every time you come back, and the world still checks it. The only thing remembered is a name.

Case-sensitive, both sides

Username and password are case-sensitive. The world does not lower-case either before hashing. The register and login cards say "Usernames and passwords are case-sensitive" so a player learns this before typing, not after a failed login.

What the world does not do

  • It never emails a password or a password hash.
  • It never logs a password to console.
  • It never returns which of username or password was wrong - the error is always the same string.
  • It never accepts plaintext "admin" or "root" backdoors - every login is checked the same way.

Bans and admin flags

The ban list rides on the account row (the old is_admin flag is history). A ban reaches both the account and any character it owns, so a banned account cannot just create a new character. Staff rank is per character and checked per command, so a change takes effect on the next thing the character tries to do.

Where the flow lives

The world owns every step of this - hashing, minting a session token, comparing, revoking. The client never hashes anything and never stores a password. See The Admin Panel for how a session ends up in a browser.
